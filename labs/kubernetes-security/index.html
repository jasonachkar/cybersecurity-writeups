    1# HARDENED admission, layer 2. Pod Security Admission (the namespace labels) covers
2# the Pod Security Standards; it does NOT require resource limits, forbid :latest,
3# require a read-only root filesystem, or restrict service-account token projection.
4# This ValidatingAdmissionPolicy (CEL, built into the API server, no webhook) adds
5# those controls. failurePolicy Fail: if the policy cannot be evaluated, deny.
6apiVersion: admissionregistration.k8s.io/v1
7kind: ValidatingAdmissionPolicy
8metadata:
9  name: lab-pod-extra-controls
10spec:
11  failurePolicy: Fail
12  matchConstraints:
13    resourceRules:
14      - apiGroups: [""]
15        apiVersions: ["v1"]
16        operations: ["CREATE", "UPDATE"]
17        resources: ["pods"]
18  variables:
19    - name: containers
20      expression: >-
21        object.spec.containers
22        + object.spec.?initContainers.orValue([])
23        + object.spec.?ephemeralContainers.orValue([])
24  validations:
25    - expression: >-
26        variables.containers.all(c,
27          has(c.resources) && has(c.resources.limits)
28          && has(c.resources.limits.cpu) && has(c.resources.limits.memory))
29      message: Every container must set CPU and memory limits.
30      reason: Invalid
31    - expression: >-
32        variables.containers.all(c,
33          c.image.contains('@sha256:')
34          || (c.image.matches('^[^@]*:[^:/@]+$') && !c.image.endsWith(':latest')))
35      message: Images must be pinned by digest or carry an explicit non-latest tag.
36      reason: Invalid
37    - expression: >-
38        variables.containers.all(c, c.?securityContext.?readOnlyRootFilesystem.orValue(false) == true)
39      message: Containers must use a read-only root filesystem.
40      reason: Invalid
41    - expression: >-
42        !has(object.spec.volumes) || object.spec.volumes.all(v,
43          !(has(v.projected) && v.projected.sources.exists(s, has(s.serviceAccountToken)))
44          || (object.metadata.?labels.orValue({})[?'lab.example/api-access'].orValue('') == 'approved'
45              && object.spec.?serviceAccountName.orValue('default') != 'default'))
46      message: >-
47        A service-account token (automounted or projected) requires the reviewed
48        label lab.example/api-access=approved and a non-default ServiceAccount.
49      reason: Forbidden

    Scope¶

    One question: what can a compromised workload do, as seen from inside the cluster, and which control changes the answer? Four properties are measured on an insecure baseline and a hardened equivalent, using the same application image family as the Docker lab:

    Property How it is measured
    Workload identity A k8sprobe subcommand in the pod calls the API with the pod's own token and records HTTP status codes and item counts only (never names or values), plus SelfSubjectAccessReview for write permissions so it changes nothing
    Permissions kubectl auth can-i as the ServiceAccount, cross-checked against the in-pod result
    Network reachability tcpcheck from inside each pod to a data-tier canary, another tenant's canary, and the API server endpoint
    Runtime constraints The Docker lab's probe run inside the pod: uid, capabilities, NoNewPrivs, seccomp, read-only root, cgroup limits, denied syscalls

    Out of scope: multi-node scheduling, node hardening, etcd encryption, API-server audit logging, service mesh, cloud IAM, and any cluster that is not the kind cluster this lab creates and deletes. A namespace, a PSA label or a NetworkPolicy is not a hostile multi-tenant boundary; see the Kubernetes multi-tenancy research.

    NetworkPolicy enforcement is a property of the CNI¶

    Writing NetworkPolicy objects proves nothing; the API server accepts them whether or not anything enforces them. The Kubernetes documentation says so directly (source-reviewed): a policy without a controller that implements it "will have no effect".

    I observed this. With kind's default CNI on this VM, a default-deny Ingress+Egress policy changed nothing: the client kept reaching the server 30 seconds later. The CNI's policy controller logged netlink receive: no such file or directory while programming nftables, which I believe means this kernel lacks an nftables capability it needs. That was a manual experiment, not part of the scripted run, so it is kept as a labeled one-off (observation-kindnet-no-enforcement.txt). On a kernel with full nftables support kindnet may enforce policy; I did not test that.

    The lab therefore disables the default CNI, installs Calico v3.33.0 (manifest pinned by SHA-256) and runs scripts/np-smoke.sh before anything else: the same request must succeed, then time out after a default-deny policy. The orchestrator aborts if it does not. Every "blocked" result above is conditional on that test having passed (np-smoke.json: before_policy_reachable: true, after_default_deny_reachable: false).

    Enforcement demonstrated¶

    policies/hardened-pods.yaml denies:

    • privileged containers and privilege escalation;
    • host PID, IPC, or network namespaces;
    • hostPath volumes;
    • added Linux capabilities or failure to drop ALL;
    • writable root filesystems;
    • missing non-root and seccomp configuration;
    • missing CPU/memory requests or limits; and
    • service-account token automount unless explicitly disabled.

    The accepted Pod is tested alongside privileged, host-namespace, hostPath, capability, missing-resource, and token-automount negative fixtures.

    policies/verify-release-images.yaml uses the stable Kyverno 1.18 policies.kyverno.io/v1 ImageValidatingPolicy. It constrains repository, keyless issuer, full workflow-and-branch subject, SLSA provenance predicate type, required verification, digest verification, and failurePolicy: Fail. Separate :* and @sha256:* globs make tagged and digest references to the exact repository eligible for evaluation while excluding lookalike repositories.

    On 2026-07-23, the manifest conformed to Kyverno v1.18.2's official ImageValidatingPolicy CRD v1 schema. The downloaded CRD asset SHA-256 was 3528151f3717c9946ee56d60866f2cf6c29a4b1a7e759c72af60451147b995c2. The Node harness separately evaluates eleven synthetic, already-resolved evidence claim sets. It returns false for unsigned, wrong repository/workflow/branch/issuer/predicate, missing or malformed provenance, verifier/transparency failure, and digest mismatch.

    The twelfth case proves only that a tag such as :latest matches the reviewed tag selector. Its admission result is deliberately null: the harness does not model registry resolution or Kyverno's mutateDigest behavior and therefore makes no accept/deny claim for tag-only input. This is a schema-validated example; no live enforcement test. Signature, certificate, registry, transparency-log, mutation, webhook failure, and controller behavior were not executed.

    Network boundary¶

    fixtures/network-policies.yaml contains namespace-wide default-deny ingress and egress plus an explicit DNS exception. NetworkPolicy has an effect only when the selected CNI implements it. DNS labels, ports, node-local DNS paths, dual-stack behavior, and required application egress must be verified in each cluster. NetworkPolicy does not control all host-network, node, service-mesh, or cloud-network paths.

    Operational rollout¶

    Use observe → audit → warn → enforce → measure bypasses. Track policy evaluation errors, denials, exceptions and expiry, unsigned-image attempts, registry/rekor availability, admission latency, and workloads that require a separate runtime class or cluster. Keep a reviewed break-glass path outside tenant administrator control.

    What was not tested¶

    • A multi-node cluster, scheduling constraints, node-to-node policy paths, and NetworkPolicy behaviour across nodes.
    • Kyverno or OPA Gatekeeper running as live admission controllers. Both ran offline only. Webhook latency, failurePolicy behaviour under outage, background scans and exceptions were not exercised. The ValidatingAdmissionPolicy is the only non-PSA live admission control.
    • Signed-image admission. The ImageValidatingPolicy and its model are unchanged; no signature was verified in a cluster.
    • Other CNIs, and kindnet on a kernel where it works, NetworkPolicy features beyond L3/L4 allow rules (named ports, SCTP, endPort, FQDN or L7 policy), IPv6, and egress to cloud metadata endpoints.
    • API-server audit logging. The Audit action on the VAP binding was set but no audit sink was configured, so I cannot show the records.
    • Token theft and replay. The lab shows what an identity can do; it does not test token exfiltration, TokenReview of a deleted pod's token, or revocation timing.
    • Pod Security Admission exemptions and cluster-wide defaults (an AdmissionConfiguration), and PSA at versions other than v1.37.
    • seccomp Localhost profiles (the Docker lab's profile on a node). The hardened pods use RuntimeDefault.
    • Cloud-managed Kubernetes (EKS, AKS, GKE) and their identity federation. Nothing here contacts a cloud provider.
    • Hosted CI. run-cluster-lab.sh is not part of any workflow.
    • Measured time to detect, time to contain, false-positive rates over real workloads, and cost are not measured in this lab.

    Production considerations¶

    Rollout. Do not turn on enforce first. For PSA: warn and audit at restricted per namespace, read the warnings for a release cycle, fix or exempt, then enforce; keep the version label pinned and bump it deliberately after a cluster upgrade. For a ValidatingAdmissionPolicy: bind with Warn or Audit before Deny. For RBAC: start from what the workload was observed to call, not from a built-in role. For NetworkPolicy: introduce default-deny last per namespace, after the allow rules for DNS and the real dependencies are in place and tested; the failure mode is a silent timeout.

    False positives. Observed here: the Kyverno policy rejecting pod-level runAsNonRoot; offline engines denying a pod whose ServiceAccount already disables the token. Expected in practice: :latest and digest-only references tripping naive tag rules, init containers and sidecars with legitimate NET_BIND_SERVICE or NET_ADMIN, and operators that need hostPath. Give exceptions an owner and an expiry; the allow-list is where the policy is actually decided.

    Detection. The denial is the signal, but only if you collect it: a rejected Pod created by a controller appears as a FailedCreate event on the ReplicaSet, not at kubectl apply. Alert on those events, on new ClusterRoleBindings, on pods/exec use, and on any pod that projects a token. I did not test an audit pipeline or a runtime sensor here.

    Operability. failurePolicy: Fail is correct for a security control and an outage for the control plane if the policy cannot be evaluated; the built-in VAP removes a webhook as a failure domain, which is its main operational advantage over a webhook engine. Default-deny egress needs DNS and API-server rules that depend on the CNI's view of the destination (Calico matched the post-DNAT node IP, so the policy needed the endpoint address); re-check after control-plane changes. Short-lived projected tokens are refreshed by the kubelet, so applications must re-read the file.

    Blast radius. A namespace is a policy scope, not an isolation boundary: pods share the node kernel, and the controls above shrink what a compromised pod can reach, not whether a kernel bug is exploitable. For hostile tenants, add a sandboxed runtime or separate clusters.

    Rollback. Everything is declarative. Remove the VAP binding or set its action back to Warn, relabel the namespace to warn, or delete the NetworkPolicy. Do not roll back by granting a broader role to make a deploy work; that is how the baseline was created.
